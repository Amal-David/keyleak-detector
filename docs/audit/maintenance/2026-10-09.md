scanner failure handling, and the legacy web scanner's request and report

## Findings addressed

- **Action reports and failures:** Each requested scanner runs once to a
  canonical JSON report. Every requested output format and action verdict
  derives from that report. Scanner failures, malformed reports, inconsistent
  counts, and inconsistent verdicts produce a failure instead of an apparent
  clean result. `fail-on` continues to control the exit threshold.
- **Action execution boundary:** Scanner execution and report rendering use
  isolated Python imports, including ignoring inherited `PYTHONPATH`, so modules
  in the scanned checkout cannot shadow trusted modules. Reports
  are written to a private temporary directory outside the checkout, and only
  generated paths are uploaded.
- **Release permissions:** Distribution building runs without OIDC permission.
  A separate publishing job receives only the built artifact and the OIDC
  permission needed for the existing trusted-publishing action.
- **Legacy web credentials and egress:** Proxy hooks check upstream targets
  and scope supplied credentials to the initial scheme, host, and port. A
  private per-scan marker is removed before forwarding. Cross-origin requests
  lose operator credentials, and overlapping legacy scans receive HTTP 409
  before shared findings or proxy state can mix.
- **Legacy response redaction:** JSON and SSE responses use normalized findings,
  including grouped attack-surface data. Matched secrets in surrounding context
  and normalized credential forms in errors are scrubbed.
- **Browser analyzer availability:** A missing, rejected, or invalid analyzer
  result raises a scan error. The browser scanner awaits the actual asynchronous
  analyzer before validating its result.
- **CI validation:** CI installs the lock, checks package consistency, builds
  the distributions, and requires the entire test suite to execute. A skipped
  Chromium/CDP integration test fails CI rather than silently passing.

The local Chromium download returned an HTML response rather than the official
archive, so the real browser test could not execute locally. The replacement
PR must pass CI, including browser installation and the no-skip test gate,
before merge. The PR's checks are the authoritative record of that run; the

real Chromium to capture and redact a secret present only in a fetched response
body.

The first PR CI run successfully installed Chromium and executed all 326 tests,
including that browser fixture. It exposed one additional action regression:
an inherited `PYTHONPATH=.` let the scanner import a module from the hostile
test checkout. Scanner commands now use `python -I -m keyleak.cli`, matching
the report renderer's isolation. The regression explicitly retains the hostile
import path; all 12 focused action/release tests pass with that environment.
A separate local scan using the real installed CLI and hostile checkout also
returned a valid report without importing the target's modules. The corrected
PR revision still requires a complete successful CI run before merge.

## Remaining boundaries

- The new mitmproxy hook tests use mocked transport and browser objects. They
  verify policy, origin scoping, scan serialization, and redaction, but do not
  establish end-to-end operation with a real mitmproxy installation.
- Target validation is a DNS precheck, not connection-time IP pinning. DNS
  rebinding remains a limitation, and separate recon transports need their own
  coverage.
- Chromium runtime sandboxing and the current root-based container deployment
  remain hardening work. Updating the browser does not supply operating-system
  isolation.
- Analyzer availability does not prove complete CDP, crawl, or storage coverage.
  Resource-exhaustion limits for untrusted archives also need further review.
- Advisory feeds and registry hashes do not prove that upstream code or build
  tooling is harmless. Future maintenance should review release changes,
  provenance, permissions, and behavior alongside automated checks.
